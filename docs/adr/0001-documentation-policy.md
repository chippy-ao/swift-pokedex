# ADR-0001: ドキュメント運用方針

- ステータス: 承認済み
- 日付: 2026-10-28

## コンテキスト

swift-pokedex は個人の学習用プロジェクトで、計画段階です。開発者と AI (Claude Code) の 2 人で進めます。ドキュメントを 1 か所にまとめると、変わりにくい設計ルールと、頻繁に変わる仕様やタスクが混ざって古くなりやすくなります。また、同じ内容を複数の場所に書くと、片方だけ更新されて食い違います。置き場所と、ADR を残す基準を最初に決めておく必要があります。

## 決定

- 情報は性質ごとに、ADR / `docs/` / 各パッケージの README / ルートの README / CLAUDE.md / GitHub Issues に分けて置きます。
- 「同じことは 2 か所に書かない」「理由は決めたものの近くに書く」の 2 つのルールを守ります。
- ADR は、開発者と AI が合意した、構造に関わる決定だけを残します。作業のたびには書きません。
- 置き場所の表、2 つのルール、ADR を残す基準の詳細は [docs/README.md](../README.md#ドキュメントの運用ルール) に一本化します。

## 理由

- 同じことを 1 か所にしか書かなければ、更新漏れによる食い違いが起きません。
- ADR は検討した代替案と却下の理由を残します。リポジトリ内にあり AI が読めるため、AI が却下済みの案を再提案するのを防げます。
- Nygard が指摘する、経緯が分からないまま決定を「盲目的に受け入れる」ことも、理由を知らずに「盲目的に変更する」ことも避けられます。
- 学習用プロジェクトなので、決定の経緯そのものが学びになります。
- 残す対象を合意したものに絞れば、ADR が増えすぎず、読まれ続けます。
- タスクを Markdown に書くと状態管理が二重になるため、Issues / Milestones に一本化します。

## 検討した代替案

| 案 | 不採用理由 |
| --- | --- |
| 全部を 1 つの README に書く | 性質の違う情報が混ざり、更新頻度の差で古くなる |
| ロードマップを docs に Markdown で書く | Issues と二重管理になり、進捗が更新されなくなる |
| 機能仕様を docs/ に集約する | コードと別 PR になりやすく乖離する |
| ADR を作らず docs を直接書き換える | 「なぜそうしたか」が失われる |
| 作業のたびに ADR を書く | 書く負担が大きく、重要な決定が埋もれる。判断の軽いものは Issue / PR で足りる |
| ADR を作らず docs と PR だけにする (開発者の Flutter プロジェクトの運用) | PR は後から探しにくく、却下した案が AI から見えず再提案されやすい。学習用として経緯を一覧で読み返せない |

## 影響

### 良い点

- 情報の置き場所に迷わない。
- 設計変更の履歴と却下した案が ADR として残り、AI も参照できる。

### 悪い点・注意点

- feature の挙動を変えたときに README を更新し忘れないよう、PR で確認する必要がある。
- ADR は書き換え不可なので、軽微な方針変更でも新しい ADR が必要になる。
- ADR にするかどうかは、その都度開発者と AI が合意する必要がある。
