# ADR-0001: ドキュメント運用方針

- ステータス: 承認済み
- 日付: 2026-10-27

## コンテキスト

swift-pokedex は個人の学習用プロジェクトで、計画段階です。ドキュメントを 1 か所にまとめると、変わりにくい設計ルールと、頻繁に変わる仕様やタスクが混ざって古くなりやすくなります。更新頻度と置き場所を最初に決めておく必要があります。

## 決定

情報の性質ごとに置き場所を分けます。

| 種類 | 置き場所 | 更新ルール |
| --- | --- | --- |
| 変わりにくい設計ルール | `docs/` | 設計が変わったときに更新する |
| 決定の経緯 | `docs/adr/` | 書き換えない。覆すときは新しい ADR を追加し、古い ADR を Superseded にする |
| 機能仕様 | 各 feature の `README.md` | コードと同じ PR で更新する |
| ロードマップ・タスク | GitHub Issues + Milestones | ドキュメントにはしない |

docs にはフェーズの一覧と [Milestones ページ](https://github.com/chippy-ao/swift-pokedex/milestones)へのリンクだけを書きます。

## 理由

- 仕様をコードと同じ PR で更新すれば、乖離に気づきやすくなります。
- 経緯を ADR に分離すると、docs 本体は「今どうなっているか」だけを書けます。
- タスクを Markdown に書くと状態管理が二重になるため、Issues に一本化します。

## 検討した代替案

| 案 | 不採用理由 |
| --- | --- |
| 全部を 1 つの README に書く | 性質の違う情報が混ざり、更新頻度の差で古くなる |
| ロードマップを docs に Markdown で書く | Issues と二重管理になり、進捗が更新されなくなる |
| 機能仕様を docs/ に集約する | コードと別 PR になりやすく乖離する |
| ADR を作らず docs を直接書き換える | 「なぜそうしたか」が失われる |

## 影響

### 良い点

- 情報の置き場所に迷わない。
- 設計変更の履歴が ADR として残る。

### 悪い点・注意点

- feature の仕様変更時に README を更新し忘れないよう、PR で確認する必要がある。
- ADR は書き換え不可なので、軽微な方針変更でも新しい ADR が必要になる。
